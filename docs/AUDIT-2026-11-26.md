## The short answer

**The app is in better shape than most AI-written software.** The core
security design is sound and the accounting engine has many safeguards. There
are **three things to fix before go-live** (all quick), a handful of medium
items, and one process change that matters more than any single bug.

| Area | Grade | One-line verdict |

## Fix before go-live

### SEC-01 — Demo admin account with a published password  *(High)*

The setup script (`npm run db:seed`), which the deployment guide tells you to
run on the production server, creates two logins:

- `admin@demo.com` / `admin123` (full administrator)
- `cashier@demo.com` / `cashier123`

These passwords are written in the public code and the deployment guide. Worse,
**every time the script runs again it resets those passwords back to the demo
values, re-activates the accounts and restores admin rights**, even if you had
disabled them. The accounts are also never forced to choose a new password.

**Risk:** anyone on your office network who knows the default can log in as
administrator and see or change all the books.

**Fix:** the production setup must not create demo users. If a first admin is
needed, give it a random one-time password that must be changed on first login,
and never overwrite an existing user's password on a re-run.

> **Do now:** the October notes (`docs/DEPLOYMENT-20261008.md`) show a Windows
> Docker install and a homelab recovery copy. If either is still running, sign in
> and deactivate `admin@demo.com` and `cashier@demo.com`, or change their passwords.

### SEC-02 — The login-signing secret is not checked for strength  *(High)*

Every login session is signed with a secret (`JWT_SECRET`). The app only checks
that the secret is *not empty*. If someone copies the example value from
`.env.example`, or uses a short word, **anyone can forge a login as any user,
including the administrator, without a password.**

**Fix:** refuse to start when the secret is shorter than 32 characters or matches
an example value, and put the command to generate one in the deployment guide.

### SEC-03 — The code repository is public  *(Owner decision)*

`hunterich/MSM-Accounting` is visible to anyone on the internet. It carries a GPL-3
open-source licence, so this may be intentional. Either way, know what is published:

- all source code, including the default passwords above;
- a personal email address (the backup administrator) in `deploy/.env.example`;
- home-network details (an internal IP address, machine name and Linux username)
  in `docs/RECOVERY-DRILL.md`, `docs/DEPLOYMENT-20261008.md`, `ROADMAP.md`,
  `CHANGELOG.md` and `scripts/recovery/`.

I scanned the full git history: **no real passwords, keys or database dumps were
ever committed.** The internal IP address cannot be reached from the internet.

**Decide:** if the app is a private business tool, make the repository private
(GitHub → Settings → General → Danger Zone → Change visibility). If it stays
open-source, replace the personal and network details with placeholders.

## Medium

### SEC-04 — Asset disposal can save an unbalanced journal  *(Accounting)*

Almost every posting goes through one central helper that refuses to save a
journal unless debits equal credits. **Disposing of a fixed asset skips that
helper.** It also *guesses* the gain/loss account by searching account names for
words like "pendapatan lain" or "beban lain". In #232 that same guessing was
removed from depreciation for exactly this reason.

**Risk:** if an asset's book value does not exactly equal cost minus accumulated
depreciation (the old #232 bug could cause that), the disposal saves a journal
that does not balance, and the Trial Balance goes out with no warning at the time.
A name match could also post the gain or loss to the wrong account.

**Fix:** post disposals through the central balanced-journal helper, take
gain/loss accounts from the asset category settings, and refuse when they are
missing. File: `src/app/api/v1/assets/[id]/dispose/route.ts`.

### SEC-05 — Demo customers, vendors and items go into the real company

The same setup script adds fake records ("Acme Corp", "Stark Industries",
"Supplier Alpha"…) to the company it creates. On a production server those would
sit in your real books and reports.

**Fix:** split the script into *essential setup* (chart of accounts, roles, tax
settings) and *demo data*, and run demo data only on test machines.

### SEC-06 — Outdated libraries with known (moderate) issues

`npm audit` reports 6 moderate advisories: three in Next.js (the server framework)
and three in libraries that Google sign-in uses. **None is serious for this app as
it is set up**: the affected Next.js features (image optimisation, "Edge" routes,
forwarding outside web responses) are not used. But the automated check on GitHub
only fails on *high* severity, so moderate issues build up without anyone being told.

**Fix:** run `npm audit fix`, confirm the tests still pass, and upgrade Next.js
before go-live.

## Low (hardening, schedule after go-live)

### SEC-07 — Small hardening items

1. **Logging out doesn't end the session on the server.** It removes the browser's
   cookie, but a copied cookie keeps working for up to 8 hours (longer if
   refreshed), or until the user changes their password. Fine on an office
   network; worth adding before any internet-facing use.
2. **Unexpected errors show internal details.** When something breaks, the raw
   technical message (sometimes including database table or field names) is sent
   to the screen. Show a generic message and log the details on the server.
3. **No size limit on bank statement or supplier-bill PDF uploads.** A comment in
   `next.config.mjs` says requests are limited to 10 MB, but that setting does not
   apply to these uploads. A very large file could slow or crash the server. Add
   the same kind of size check that supplier-bill *image* uploads already have.
4. **Email templates.** The template preview shows stored HTML as-is, and
   customer names are inserted into outgoing emails without escaping. The
   browser security policy blocks scripts, so the realistic impact is a broken or
   misleading email, not a break-in.
5. **Sign-in email is case-sensitive.** Accounts are saved in lowercase, but the
   login form looks up exactly what was typed, so `Budi@company.com` fails while
   `budi@company.com` works. This is a usability issue, not a security one.
6. **Sign-in timing.** An unknown email is rejected slightly faster than a wrong
   password, which could reveal which emails have accounts. This is minor on an
   office network.

## Process

### SEC-08 — Nobody reviews the code before it is merged

All 275 merged pull requests were written by AI and approved without a human or
AI reading the code. The only safety net is the automated test run on GitHub.
That safety net is good: every recent change on `main` passed all four test
groups. But tests only catch what someone thought to test. Every finding in this
report (SEC-01, 02, 04, 05) had passed those tests.

**Recommended:**

1. Turn on **branch protection** for `main` (GitHub → Settings → Branches) so
   nothing merges unless all CI checks pass.
2. Have every pull request **reviewed by a second AI** that writes a short
   plain-language summary for you: what changed, what could go wrong, and
   approve/don't approve. You read the summary; you don't need to read the code.
3. Have your **finance reviewer** sign off on any change that touches posting,
   tax or reports. The roadmap already asks for this. It needs to actually happen.

## What is already done well

This list is what you can rely on, and what any future change must not break:

- **Passwords** are stored with bcrypt (a slow, salted hash). Ten failed attempts
  lock the account for 15 minutes.
- **Sessions** sit in a cookie that page scripts cannot read. They are re-checked
  against the database on every request, so a deactivated user or removed role
  loses access immediately, and a password change signs out every device.
- **Permissions** are enforced on the server for every screen and every action,
  including read-only views (#234). An automated test fails the build if a new
  route forgets its permission check.
- **Staff cannot promote themselves.** Only an administrator can create, assign
  or edit an admin-level role, and a company can never be left with no admin.
- **Approvals** block self-approval, and two people approving at the same moment
  cannot post the same document twice.
- **Company separation:** every record lookup is filtered by company. I checked
  each route that loads a record by ID and found no leaks.
- **Money** is stored as exact decimals in every table (no floating point anywhere).
- **Journals:** manual journals, imports and the data-migration opening balance
  all refuse to save unless debits equal credits. Closed periods and closed
  fiscal years are locked for every posting path (#263). Posted journals cannot be
  edited, only reversed.
- **Backups** can only be run, downloaded or restored by named platform
  administrators set on the server, not by any company admin. A full restore drill
  was done in October (`docs/RECOVERY-DRILL.md`).
- **Web security headers** (HTTPS enforcement, a strict content policy, anti-framing)
  are set in `deploy/Caddyfile`.
- **No SQL injection paths found.** All database queries use safe parameter
  binding; the few raw fragments use fixed internal names only.

## How this audit was done

- Read the security-critical code end to end: request middleware, login/Google
  sign-in/refresh/logout, permission checks, role and user management, approvals,
  backup/restore, file uploads, email templates, deployment configuration.
- Scanned all 209 API route files automatically for missing company filters and
  missing permission checks, then read each one flagged.
- Traced every place that writes journal entries, to confirm each enforces
  debits = credits.
- Scanned the full git history (165 commits) for committed passwords, keys and
  database dumps.
- Ran `npm audit`, the TypeScript check and the unit test suite: **1,728 of 1,728
  tests passed**. Five test files could not load here because the spreadsheet
  library is downloaded from a site this audit environment blocks. They are
  unrelated to the findings and pass on GitHub.
- **Not run here:** the PostgreSQL integration tests and the browser tests, which
  need a database. GitHub ran both successfully on every recent change to `main`.
- **Not covered:** the frontend screens in detail, the POS app, payroll and tax
  calculations versus Indonesian regulations, and performance. Payroll and tax
  correctness needs a finance or tax reviewer, not a code review.

Codebase at audit time: commit `31e698c`, about 106,000 lines of application
code, 98 database tables, 41 migrations.
